This section will list all of the major changes that happened with the release of **Momentum 5.3.1**. Depending on installation type, all changes may not be applicable

<a name="changelog.5.3.1.table"></a>

| Type | Ticket | Description |
| --- | --- | --- |
| Enhancement | I-1651 | The **experimental** [DKIM2](/momentum/4/dkim2) module now implements the **-06** draft version of the specification. Because what is hashed and signed changed, signatures do not verify between Momentum 5.3.0 and 5.3.1 in either direction for Ed25519 signatures, for messages with a body line starting with `.`, and for messages carrying a header field whose hashing changed, such as `Received-SPF`. |
| Feature | I-1651 | DKIM2 [signing](/momentum/4/dkim2/sign) now refuses, by default, a recipe whose header-field keys are not lower case, a `mi_hash_algorithms` list naming anything other than `sha256` or `sha512` or naming one twice, and more than two `sig_sets` for one algorithm; policy scripts that did this under 5.3.0 fail to sign after the upgrade. [Verification](/momentum/4/dkim2/verify) returns `permerror` for a `Message-Instance` naming `sha256` or `sha512` twice and for a signature carrying more than two sig-sets for one algorithm, and reads a recipe key that is not lower case as if it were. The new `on_recipe_key_case` and `on_bad_hash_algorithm` options, on `sign()` and `verify()`, choose the behavior. |
| Feature | I-1705 | DKIM2 [verification](/momentum/4/dkim2/verify) now checks every signature on a message, not only the highest, and the `verify()` result has a new shape that is not compatible with 5.3.0: each entry of `signatures` has its own verdict, and reasons have new names, such as `body_hash_mismatch` and `key_missing`. Policy scripts that read the result must change. |
| Feature | I-1705 | DKIM2 [Authentication-Results](/momentum/4/dkim2/ar-clauses) has one clause for each signature checked and one for each problem no signature accounts for, with the `reason=` text of the draft and no extra overall clause. `header.s`, `header.mf` and `header.rt` are usually written as quoted-strings. |
| Feature | I-1705 | The DKIM2 options `require_recipe` for [signing](/momentum/4/dkim2/sign) and `reject_body_redaction` for [verification](/momentum/4/dkim2/verify) replace `allow_missing_recipe` and `allow_body_redaction`, which are now rejected with an error naming the new option. The defaults changed: `sign()` signs a changed message that has no recipe with the recipe `{"b":null}`, and `verify()` accepts such a message without verifying the earlier body; 5.3.0 refused both. Set the new option to `true` to keep the 5.3.0 behavior. |
| Feature | I-1705 | DKIM2 [`sign()`](/momentum/4/dkim2/sign) returns a third value on failure, a `refusal` table naming why it refused to sign, and its `info` table names a chain break in `reason`. A null sender after a signature with `rt=`, and a previous `nd=` that does not name the signing domain, are now chain breaks, and a call with `next_domain` fails on a chain break; 5.3.0 did not check those. A failed `sign()` now leaves the message unchanged: a bridge signature it added is removed. |
| Feature | I-1705 | DKIM2 [verification](/momentum/4/dkim2/verify) now rejects an Ed25519 key record whose `p=` is a DER SubjectPublicKeyInfo instead of the raw 32-byte key (reason `key_syntax`), and an RSA key over 4096 bits; 5.3.0 accepted both. A signature with one sig-set that verifies and another that does not is now a `fail` with reason `sig_partial`; 5.3.0 passed it. |
| Feature | I-1705 | DKIM2 [`sign()`](/momentum/4/dkim2/sign) and [`verify()`](/momentum/4/dkim2/verify) now fail with an error naming the option when an option has a value of the wrong type, where 5.3.0 ignored the value or read it differently. For example, `emit_debug_headers = "false"` turned the debug headers on in 5.3.0 and is now an error. `authservid` must be a host name or a token. Policy scripts that did this under 5.3.0 fail after the upgrade. |
| Fix | I-1678 | Fixed SMTP smuggling when relaying a message with a line that starts with `.` right after a bare CR or LF. Momentum wrote that line ending as CRLF without dot-stuffing the line, so a lone `.` ended the message at the next hop and the lines after it arrived there as SMTP commands; a line such as `.b` lost its `.`. This affected `RFC2822_Lone_LF_in_Body = fix`, a header block that ends with a bare CR or LF under any setting, a header line after a bare LF under `RFC2822_Lone_LF_in_Headers = fix`, a line after a MIME closing boundary that ends in a bare LF when a policy fully parses the message, and messages forwarded with Lua `msg:forward()`. |
| Fix | I-1678 | Fixed a header, or the blank line after the headers, being sent twice when relaying some large messages, depending on the length of the headers. |
| Fix | I-1683 | Fixed message parts that have a line over the length limit when `RFC2822_Max_Line_Length = fix`: with `RFC2822_Lone_LF_in_Body = fix`, their bare CR and LF line endings are now written as CRLF, and lines within the limit are no longer split. Before, a 997-character line was split inside its CRLF and a 998-character line got an empty line inserted after it. |
